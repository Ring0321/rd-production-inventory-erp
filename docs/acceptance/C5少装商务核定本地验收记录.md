# C5 少装商务核定本地验收记录

日期：2026-10-14。产品：垛序 ERP。范围：原 C5 的 C5-R1，仓管提出少装清单、商务核定/退回及双端回看。不包含仓管实际减量、少装后的补扫过账或完整 C6。基线 `2d79642e463cb28b2f2c0e483cf8527a799c184e`；实现提交与 Git 远端核对在交付核定后补记。

## 1. 业务结果

仓管在异常待处理的原装车任务详情中选择具体未核验包件、填写真实原因，系统按完整计划快照计算原计划、拟减少和拟剩余包数/净重。商务在原提货单详情中核定通过或退回，仓管 Web/PDA 查询同一记录。核定结果明确显示“已核定待变更”，不把审批当成减量完成或已出库。

一包一码、原客户、原任务编号、库存和库位保持不变。司机不申请少装、不核定、不扫码、不更新库位或过账；原司机报告异常和查看更新后的同一张任务继续保留。新接口只写 `rd_loading_reduction`，不直接改变提货单数量、装车成员、占用、PCS、库存或流水。

## 3. 真实数据库与双端验证

最后完整通过的少装样本为装车任务 125、126、127，均标注本地非现场数据。第一张原计划 3 包/2800kg，仓管申请减少明确的 800kg 包，商务通过，登记拟剩余 2 包/2000kg；原任务和提货数量仍保持 3 包/2800kg。第二张模拟请求已提交但响应丢失，320 像素端保留待核；随后模拟列表暂时漏读，页面通过真实精确 GET 补回原记录并核定原请求，未发送第二次申请，商务可退回。第三张含已核验后转异常的成员，不能将其当成未装包减少；同版本两个申请在真实 MySQL 上只建立一份有效清单。

在申请/核定阶段，比较任务、任务成员、提货主/明细、装车占用、PCS、库位、库存批次、库存流水及扫码记录的完整前后指纹，结果一致。该证明只覆盖核定记录写入阶段。随后专门对隔离样本增加包件版本模拟 ABA：历史批准显示已失效，新的当前版本申请仍可建立，不能被失效批准阻塞；这项故障注入是测试主动改变样本版本，不冒充生产现场无变化。

原仓管退回任务后，旧申请显示已失效；商务不能通过旧版本，但可以退回关闭。重复同键同内容申请恢复原结果，换内容或换操作人不能复用；重复同结论核定不会覆盖其他批准。独立商务权限与岗位、审计旧派单权限旁路、司机及其他岗位越权、本人核定、全量清零、已核验成员、关联错包均检查。

## 4. 复核及修复

1. 首次独立只读复核提出五项：逐条提货明细关联/数量不足；批准后物理状态失效未反映；旧审计角色派单权限旁路；未固化包件版本/占用身份；失联恢复受最近 100 条列表限制。已分别补逐明细校验、包件版本/claim ID 与失效读取、真实岗位和权限双校验、精确 ID/原幂等键 GET；新增红绿测试、实际 API 核查。
2. 后续独立复核确认上述指定项未见明确残留，又发现“读取已失效但活跃申请拦截仍阻止重提”的 P2。已统一创建活跃拦截与物理失效口径；目标测试先失败、完整 reactor 后通过，真实包件版本注入与重提也通过。
3. 新面板将六位净重以十进制字符串传递和显示，时间戳按原日期工具展示；手机状态标签等待真实入场动画稳定再验宽度/不透明度，未暂停动画或强制点击。已检查桌面及 390/320 图片。
   补做列表暂时漏读时发现：精确 GET 虽核对原请求，但结果未补回当前页面，会再次显示申请入口。已先以单测复现，再将身份/上下文匹配的真实回执加入当前记录；前端337项重跑及最后实际故障恢复通过，不保留未经重读的过期数据。
4. 首轮目标测试的 Mockito 变长参数桩未匹配，已改为具体权限/岗位合同。全量测试曾受旧 Byte Buddy 的 Java 21 识别限制，使用单次 Maven `-Dnet.bytebuddy.experimental=true` 后重跑通过，不修改项目 Java 17 编译目标或依赖架构。JAR 曾因服务占用无法重打包，校验并只停止该受管本地后台后重建，再启动最新服务。
5. 浏览器脚本先后修正测试账号密码长度、Web 详情 `mode=view` 合同、Element Plus 隐藏原生 checkbox 的附着条件及可见 label 正常点击。旧失败日志仍在本地，只有最后 PASS 的 `result.json` 和成功截图作为当前交付证据。
