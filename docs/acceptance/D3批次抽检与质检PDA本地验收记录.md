## 2. 实际使用流程

1. 质检人员由岗位首页进入独立 `/pda/quality`；不显示 Web 后台侧栏、标签菜单或库位过账控件。
2. 扫/输入同一真实生产产出下的任意包码，读取货物、同来源候选和已有活动检验单。查询不改变包状态、版本、库存或扫码流水。
3. 默认仅选可检的扫码包。使用“选择可检整批”可跨页读取并选择本来源全部可检包，再剔除本次未实际覆盖的包；已通过、在库或被其他检验单占用的包不自动纳入。
4. 独立选择实际抽样包，录入各样包的项目、实测值、标准上下限、单位和备注。系统不虚构抽检比例，也不将整条混合生产任务视为同一合格范围。
5. 保存并提交建立实际成员快照、活动质检占用和检测项目，仅所选成员转为 `QC_PENDING`。一包一码、原包号、原净重及生产来源不改变。
6. 另一位有复核权限的人员确认通过或填写不通过原因。服务端按实测值判定，不能靠客户端 `qualified=true` 绕过；提交人不能自审。
7. 通过的实际覆盖包转为 `QC_PASSED`，进入待上架货物池；不通过转为 `QC_REJECTED`，不能上架。未选包不继承该单结论。
8. 每一包的内部追溯可看到实际检验单、覆盖数量、抽样数量及本包是否抽样，质检记录精确打开该单。公开接口不新增客户、其他包、库位、人员或内部操作信息。

扫码定位包不必强制成为本次检验成员：已检过的包仍可用于找到同来源余包，代表包改取本次真实覆盖清单中的一包，不能再次放行已检包。

## 4. 异常和事务验证

PDA 在首次请求前，将原请求编号、成员、样包和实测项目按当前用户/有效租户保存到本机。响应断开后保留原内容；刷新再试仍发送同一请求。服务端返回同一检验单，不再次占用、建单或计算放行次数。已经返回检验单 ID 或结果未知时不能擅自释放编号；明确拒绝未创建请求时，表单恢复可修改状态。

真实浏览器验证拦截的是服务端已经成功处理的 create-batch 响应，再断开连接；不是仅模拟前端成功。重试前数据库确实存在 DRAFT，重载重试后为 SUBMITTED，两次请求内容完全相同。

事务领域记录与检验单、成员和包状态同提交。原系统异步操作日志仅作辅助，不能替代必要领域审计。MySQL 故障注入实际覆盖：

- 第二个成员转 QC_PENDING 失败：第一个成员、检验单、时间及版本全部回滚。
- 第二个成员转 QC_PASSED 失败：整份复核回滚，不出现半批放行。
- CREATE 审计失败：不留下检验单、成员占用或新增孤立检测项目，原请求可正常重试。
- SUBMIT 审计失败：包仍待检、单仍 DRAFT，已有 CREATE 事件不变。
- APPROVE 审计失败：包仍待复核、单仍 SUBMITTED，活动占用不提前释放。
- REJECT 审计失败：原单、成员状态、复核元数据和审计记录不变，健康重试后才拒绝并释放。

触发器仅针对本轮标记包/检验单/请求编号，在 `finally` 中清除；运行后核对不存在测试触发器。全部在隔离本地库完成，不用于生产库。
