## 4. 集成修复与独立复核

1. Windows旧C++运行库不能在主JVM安全执行新版OR-Tools。保留原拒绝保护，计算改由受信任Java启动同一fat-JAR的纯JSON子进程；6秒硬时限、输入/输出/并发上限、原事实结果复核、环境白名单，不传数据库和GLM凭据。
2. 实际fat-JAR首次原生提取不可用：按Spring Boot官方`requiresUnpack`合同处理平台资源JAR，再用最终产物验证成功。Maven打包被运行JAR锁定时仅停止经过PID/命令核对的应用，不动MySQL/Garnet数据。
3. MyBatis租户解析器不接受裸`BINARY`表达式；先新增红测试，再改为可解析的`CAST(... AS BINARY)`，精确范围及真实HTTP回归通过；没有绕过租户拦截器。
4. 禁止打印、配置发布及OCR在401续期中自动重发；实际加载共享Axios拦截器验证，无刷新、排队或重复审计。结果不明的打印继续保持挂起核对。
5. 独立复核发现并修复四项布局问题：100条选项截断、发布坐标被总览重排、未配置真实库位隐藏、编辑链接误选仓库；完整分页/原坐标/待核清单/请求仓库测试通过。相关100项定向测试通过后又跑全前端及真实页面。
6. 原包件分页不实现包号过滤；新标签工具改复用已有精确`trace`接口，3项查询回归通过，不擅自改变旧分页接口。
7. 指纹脚本曾在中文Buffer分块边界产生假差异；修复为流式UTF8，并保留首次失败，不追溯写成成功。OCR在线重装遇到TLS后停止，复用已核验本机wheel产物并重新检查依赖、边界和真实推理。

实现支持、字体支持、许可补证、运行时诊断、独立复核和四项修复支持均已接收并关闭；没有继续复用已完成的支持上下文。


脚本只允许本机9000/3310隔离实例、原合成演示和原私有账号。配置验证/浏览器验证会有意保存发布演示布局并登记一次测试补打；不是生产环境只读脚本。原图库/字节/权限的其余查询不改库存；不应直接指向正式工厂服务器。

原始证据保存在忽略的`temp/reuse-verification/`；Python真实模型证据在`tools/document-ocr/.runtime/`。通过的截图、PDF、摘要及哈希清单另存用户指定的`ERP/outputs`，失败调试图和私有环境不对外交付。

## 6. 仍开放的门槛

- C5-R2/R3、C6、原PDA/二维码完整阶段及现场试运行，均不因本专项增加完成数。
- GLM仍关闭；模型、费用上限和真实平台调用未验收。本次配吨是本地确定性求解，不伪装成GLM输出。
- 布局是人工维护的示意配置，不是自动定位、实测导航、真实通道/堆高/历史厂房还原。发布仅用于原库位显示，司机不扫码、不维护库位、不最终过账。
- 实体标签/PDA/打印机尚未采购，真实工厂网络、实际单据准确率、磨损与扫码距离、低配CPU/内存性能和本机OCR的操作系统隔离/防火墙仍待现场确认。
- 214项前端依赖的250份原始通知及固定上游补证保留。仍有fontkit/brotli/dfa/keycon/cfcs的完整原文、部分发布来源及OCR-A/B字体等缺口；不宣称全依赖商用许可审查完成。Python/native wheel及OR-Tools本地原生组件也需随正式发布保留各自通知。
- pdfme按需加载块较大，正式部署仍需结合设备性能、CSP、缓存、反向代理并发/流量上限和发布升级测试；本地构建成功不能代替这些门槛。

本次技术验收与源码归档分开记录；最终实现提交、远端核对和交付摘要见总计划及进度台账。
