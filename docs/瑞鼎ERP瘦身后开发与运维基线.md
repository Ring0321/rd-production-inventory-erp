# 瑞鼎 ERP 瘦身后开发与运维基线

## 1. 产品边界

系统名称为“瑞鼎生产库存订单ERP”，采用单公司模式，所有业务与权限数据固定归属 `tenant_id=1`。系统只管理生产后环节：炉号炉层产额、成品入库、库存、订单差额、调拨、出库和日报。

首版保留的管理能力为用户、部门、岗位、角色、字典、登录日志、操作日志和个人中心。短信、密码找回与社交登录是可选能力，只有部署配置和数据库渠道同时可用时才由 `/system/auth/capabilities` 向前端开放。

## 2. 技术架构

| 层级 | 技术 | 责任 |
| --- | --- | --- |
| Web | Vue 3、TypeScript、Vite、Element Plus、ECharts | 工作台、业务录入、查询、报表、权限路由 |
| API | Spring Boot、Spring Security、MyBatis Plus | 认证授权、业务事务、审计与并发控制 |
| 数据 | MySQL 8.4 | 权限、业务主数据、库存流水、订单履约、审计 |
| 缓存 | Redis 7 | 令牌、权限与短期缓存 |
| 调度 | Quartz | RD 日报汇总任务运行内核 |
| 部署 | Docker Compose、Nginx、Temurin JRE 21 | 四容器试运行与无源码发布 |

业务包统一放在 `com.ruiding.erp`。稳定框架层暂时保留原包名并与业务隔离，不允许继续向框架层叠加 RD 业务。

## 3. 数据与事务约束

库存以不可变流水为事实来源，台账数量是事务内同步维护的当前状态。生产入库、调整、调拨、订单匹配和出库必须在单个数据库事务内完成，并使用行锁或乐观锁避免超分配与重复确认。

销售订单至少保留以下独立字段：

- `required_qty`：销售订单应入数量。
- `actual_output_qty`：实际生产量。
- `production_difference_qty`：应入数量减实际生产量。
- `transfer_adjust_qty`：从其他库存或订单调入的数量。
- `adjusted_difference_qty`：调拨后的剩余差额。
- `fulfilled_qty`：已匹配或已履约数量。

当 `fulfilled_qty >= required_qty` 时订单进入完成/关闭状态。调拨必须同时记录调出、调入两条库存流水及来源订单、目标订单，不能直接覆盖原数量。

## 4. 数据库生命周期

全新环境只执行 `backend/sql/mysql/rd_erp_clean.sql`。该脚本只含 44 张运行必需表、固定租户、管理员占位账号、五类业务角色、精简菜单、字典和 RD 日报任务。

管理员初始密码不写入 SQL。应用首次启动发现占位密码时，从 `RD_ADMIN_INITIAL_PASSWORD` 读取并编码写入；缺少或长度不足 12 位时启动失败。

已有环境只允许按以下顺序升级：

1. 执行一致性备份并生成 SHA-256。
2. 恢复到独立数据库。
3. 记录所有 RD 表行数、关键数量汇总和校验值。
4. 执行 `rd_erp_upgrade_slim.sql` 两次，验证幂等。
5. 对比升级前后 RD 数据与用户角色关系。
6. 审批后在维护窗口执行正式升级。

## 5. 开发顺序

每个业务变更遵循：数据约束与状态机、后端服务测试、API、前端交互、权限矩阵、审计、浏览器验收。不得先加页面再补事务逻辑。

提交前最小验证：

```powershell
cd backend
mvn -pl rd-erp-server -am test

cd ../frontend
pnpm ts:check
pnpm build:prod
```

涉及库存扣减、调拨、订单匹配或出库时，还必须运行并发测试、五岗位权限测试和操作日志测试。

## 6. 发布与回滚

源码部署使用 `deploy/trial/compose.yaml`；发布 ZIP 使用 `deploy/trial/compose.runtime.yaml`。两者都加载 `rd_erp_clean.sql`，后端运行包统一为 `rd-erp-server.jar`。

发布环境必须设置数据库密码、Redis 密码和管理员初始密码。短信、社交渠道和外部密钥只从环境变量或密钥管理系统注入。发布前对工作区、完整 Git 历史、镜像层和 ZIP 各执行一次密钥扫描。

回滚只允许使用已验证的数据库备份和对应应用版本。禁止为了回滚直接删除或修改生产业务流水。

## 7. 容量演进

MySQL 足以承载当前企业 ERP。业务量增长时按“索引与慢查询治理、冷热分层、读副本、按业务日期分区、历史归档”的顺序演进。库存扣减与订单履约写路径保持单主库强一致，不通过缓存或异步消息替代事务真实性。
