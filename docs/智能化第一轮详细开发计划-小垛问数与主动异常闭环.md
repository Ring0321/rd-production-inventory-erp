## 1. 第一轮目标

把原本分散的“小垛找页面、ERP 查询、任务异常、三维库位”连接成一条可用路径：用户提出受控业务问题，系统返回授权事实和依据；后台主动发现明确规则命中的问题；用户定位原任务或实际关联库位，在原业务页面处理；系统复核原记录后更新提醒结果。

第一轮交付三个主体：

1. 小垛业务问数：明确支持的问题、范围选择、真实结果、来源和原页面入口。
2. 主动异常中心：三类规则、自动发现、去重、知悉、来源复核与处理历史。
3. 三维联动工作台：保留三维仓储为主要展示点，增加授权异常摘要、问题列表和定位联动。

不以“多一个聊天框”作为验收，不以模型措辞漂亮代替业务结果正确。

## 3. 范围与非目标

### 3.1 本轮包含

- 按权限查询当前库存、今日出入库、待检/待复核、待入库、上架和装车任务、实际占用及异常。
- 以规则主动发现质检待复核超时、装车占用异常、任务办理超时。
- 在异常详情中展示原对象、触发条件、时间、影响成员、负责岗位和原页面入口。
- 对提醒执行“已知悉”；在原业务变化后由系统重新评价，不提供“强制业务完成”。
- 按原仓库和实际 locationId 联动三维图。没有可靠位置的对象仍可看详情，不杜撰摆放点。
- 手机/电脑使用、七角色权限回归、原业务与出入库记录保护。

### 3.2 本轮不包含

- 自由生成 SQL、任意工具调用、后台自主办理业务、自动放行、自动更改库位或库存。
- 自然语言新建/审批订单、自动选货锁货、自动派单或自动替换出库成员。
- 新增配吨算法、上架优化算法、单据识别模型、全公司知识库、经营预测和设备预测。
- 企事通或智行导引的独立系统重建；本轮只保留将来关联原任务/管理事项的接口边界。
- 真实厂区硬件、相机实扫、打印验收、真实定位或承载设计。
- 自动把 C5/C6、AI-A5、现场/商用许可等原未完成项标为完成。

“能否发货”第一轮只解释已取得的具体限制及原办理入口，不给出全订单可发承诺，不代替履约核定。

## 4. 首批业务问数合同

### 4.1 支持的问题

第一轮采用本地有限意图解析加服务器白名单查询。原问句不发送模型，也不作为数据库语句；不支持的问题先澄清或引导原报表。

| 查询编号 | 示例问法 | 必须返回的结果 |
| --- | --- | --- |
| Q01 | 现在在库多少包？ | 在库、可用、锁定分开；登记重量注明单位和实际统计范围 |
| Q02 | 今天出了多少、入了多少？ | 按有效业务流水统计；作废、冲销/反向流水按原已确认口径处理 |
| Q03 | 哪些包还待检？ | 明确包件待检与质检单待提交/待复核的区别，不相互替代 |
| Q04 | 哪些质检已经提交但还没复核？ | 实际质检单、提交时间、覆盖成员及可用的原审核入口 |
| Q05 | 哪些货合格了还没入库？ | `QC_PASSED` 和 `INBOUND_PENDING` 分开，不将已派任务当已入库 |
| Q06 | 有哪些上架任务待处理？ | 真实任务阶段、计划/完成数量、负责岗位；司机仅本人任务 |
| Q07 | 哪些装车任务还没出库？ | 实际装车阶段；`PENDING_REVIEW` 不当作已出库 |
| Q08 | 哪些货正被装车任务占用？ | 有效 claim 和原任务关联；正常占用与异常提醒分开 |
| Q09 | 现在有哪些需要处理的问题？ | 当前账号可见异常、来源健康及最近成功扫描时间 |
| Q10 | 这个提醒为什么出现，下一步谁处理？ | 精确 alertId 的触发事实、阈值、岗位和允许入口；不推测真实根因 |

Q01/Q02 保留原全局口径时必须明确显示；如果用户明确问某仓库而接口尚不能正确限定，先澄清，不能返回全局数冒充指定范围。Q09/Q10 在异常链路完成前保持未开放，不展示失效按钮。

### 4.2 指标、时间与范围

- 独立包件数使用实际主键去重；Q01/Q02 原台账数量明确标为包当量，保留原六位小数，不冒充已逐包核实的整数。重量使用服务器定点数和统一 kg，保留原库精度；库存登记重量不标为实磅重量。具体口径见[指标与权限合同](小垛业务问数指标与权限合同-S1-01.md)。
- 当前库存与历史流水分开。首版日期默认“今天”，以服务器 Asia/Shanghai 自然日半开区间确定；不把当前快照回答成上周/上月库存。
- 其他时间范围先引导原报表；确需扩展时另加有界查询与专项用例，不能偷偷复用当前数。
- 一个任务多行、多条提醒和多个包件不能互相当作数量。分别定义 `alertCount`、`businessObjectCount`、`distinctPackageCount`。
- 总计由同一授权条件下的服务器聚合给出；当前页条数不等于全部条数。分页默认 20、单页最多 100；每个明细链接可继续分页追查。
- 同名仓库、重复货位简称、多个候选包码或模糊任务编号必须让用户选择；不得默认取第一条。
- 返回 `asOf`、过滤条件、权限范围说明、源版本及 `KNOWN/PARTIAL/UNAVAILABLE`。未知不填零，部分结果不标为全部。
- 原接口未提供足够数据权限时，对应新查询先禁用或补齐策略，不宣称已有按客户/部门/仓库的细粒度隔离。

## 5. 三类主动异常规则

阈值属于服务器配置，不由大模型生成。默认未核定的阈值为停用；每条规则必须带版本、实际阈值和生效时间。演示可用明确标注的短阈值，但不能作为工厂考核 SLA。

| 规则 | 首版精确定义 | 时间来源 | 正常或待核情况 |
| --- | --- | --- | --- |
| R1 `QUALITY_REVIEW_OVERDUE` | 实际质检单 `SUBMITTED`，超过已配置待复核阈值 | `submitTime` | DRAFT/CORRECTED 不用此规则；缺时间显示来源待核，不猜超时 |
| R2a `LOADING_CLAIM_OVERDUE` | 活动装车任务仍占用实际成员，最早有效占用超过已配置阈值 | 有效 claim 的 `claimedTime` | 短时正常占用只列为业务事实；无法确定成员或时间时不计算时长 |
| R2b `LOADING_CLAIM_MISMATCH` | 任务已 `OUTBOUNDED/CANCELLED`，却仍存在可确认的残留 claim | 任务终态、版本及 claim 实际关联 | 任务/成员来源不可读不等于残留成立；只上报核对，不自动释放 |
| R3a `TASK_ASSIGNMENT_OVERDUE` | 上架/装车任务处于 `ASSIGNED`，派发后超过未接办阈值 | `assignedTime` | 未派单、已经开始或缺时间不按此规则报警 |
| R3b `TASK_CONFIRMATION_OVERDUE` | 上架为 `PENDING_CONFIRMATION` 或装车为 `PENDING_REVIEW`，超过待仓管确认阈值 | `scanCompleteTime` | MOVING/LOADING 没有可靠最近进度时间，不在首版猜“无进展时长” |

R2 和 R3 可同时命中同一任务：中心按原任务聚合展示多个原因，计数同时说明“提醒条数”和“涉及任务数”，不重复声称增加包件数量。

质检按真实单据及其实际覆盖成员显示；部分抽检不能把未覆盖包件标成合格。提醒中的职责是处理岗位，不是对个人过错的判定。

### 5.1 提醒生命周期

- `OPEN`：规则命中且来源核对有效。
- `ACKNOWLEDGED`：有权人员已知悉，只改变提醒元数据，不代表原业务完成。
- `RESOLVED`：系统重新读到明确有效的原记录，确认该条件不再成立，保存具体原因。
- 读取失败、任务缺失、分页未完成或权限变化只改变来源健康/可见性，不能据此自动 RESOLVED。
- 取消、质检复核、规则停用、阈值变更分别记录实际原因；“规则不再适用”不能显示为“货物已发出”。
- 同一对象、规则和处理周期只保留一个当前提醒；重复扫描不刷屏。已消除后再次真实命中形成新周期，旧事件保留。
- 初次发现时刻不等于业务异常开始时刻；同时保存原时间锚点与发现时间。

### 5.2 主动扫描

复用当前 Quartz JobHandler 与服务层。演示环境建议每 60 秒扫描一次，前台可见时每 30 秒更新提醒摘要；正式频率在性能验证后核定。均为规则/数据查询，模型调用数必须为 0。

按显式租户和规则分页扫描，建议源分页 200；游标与单次耗时有界，分段未完成显示 PARTIAL。同步保存开始、最近成功、失败和延迟信息。普通用户查询不启动全租户扫描。

多实例或任务重入用短期租约控制，数据库唯一约束与源版本 CAS 是最终防重保障。租约丢失的旧扫描不能覆盖新结果；失败后允许幂等重扫。复查已有提醒时必须逐对象核对有效源，不能按“本页没查到”批量消除。

## 6. 架构与数据设计

### 6.1 复用原架构

前端保留 Vue/Element Plus、小垛组件和 Three.js。后端在现有 `rd-erp-inventory/com.ruiding.erp` 内增加 `workassistant`、`workalert` 业务边界；权限和事务仍由原 Spring 服务控制。新功能读取原服务/经过核对的专用只读聚合，不让模型或浏览器执行 SQL。

包件来源、任务阶段、库位和出入库最终状态仍在原表。异常表只是可重建的提醒投影和处理记录，不是新的库存表。首次迁移不得批量重写业务状态、补造业务时间或回填旧数据为“已智能处理”。

### 6.2 拟新增数据对象

| 对象 | 最少字段/职责 | 约束 |
| --- | --- | --- |
| `WorkQueryRequest/Result` | 查询枚举、受控过滤、asOf、范围、指标、分页、来源引用、数据完整性 | 原问句不外发；无任意 URL、SQL 或模型工具 |
| `rd_work_alert` | tenant、ruleCode/version、业务类型/ID、处理周期、dedupKey、状态、等级、源版本/指纹、时间锚点、发现/核对/消除时间、原因及提醒版本 | 唯一活动键、防重、版本条件更新；仅保存最少来源引用和必要证据 |
| `rd_work_alert_event` | alertId、事件类型、前后状态、操作者、时间、幂等键、原版本和受控原因 | 与提醒变更同事务；不记录密钥、聊天原文或整份业务附件 |
| `WorkAlertScanState` | 租户/规则、扫次代次、游标、开始/成功/失败时间、完整性 | 只用于扫描健康和恢复；失效不清空活动提醒 |

扫描状态持久化位置在 S1-07 冻结：优先使用提醒基础设施的轻量元数据；若复用 Redis 必须独立键前缀，不能复用或清理 AI 预算/回执键。无论存储选择如何，不允许覆盖失败记录或把缺失值当扫描成功。

### 6.3 拟定接口

`GET /rd/work-assistant/query` 已在 S1-02 开放 Q03-Q05，其余新查询返回不可用；下面的提醒接口与 JobHandler 仍为计划，未开放。

| 方法与路径 | 用途 | 数据写入与权限 |
| --- | --- | --- |
| GET `/rd/work-assistant/query` | 执行查询枚举和有界过滤 | 只读；逐查询校验原业务权限及数据范围 |
| GET `/rd/work-alert/summary` | 当前账号可见提醒计数、来源健康 | 先过滤授权对象再聚合，禁止返回全租户总量给无权角色 |
| GET `/rd/work-alert/page` | 分页查询提醒 | 默认不带无权对象名称、数量或位置 |
| GET `/rd/work-alert/get?id=...` | 读证据、事件、下一岗位、允许动作 | 重新检查原对象权限和当前版本 |
| POST `/rd/work-alert/acknowledge` | 确认已知悉 | 只写提醒及事件；携带 alertVersion 与 UUID 幂等键 |
| POST `/rd/work-alert/recheck` | 请求复核一个已授权提醒 | 可更新提醒投影，不能修改源业务；限频且不触发全仓扫描 |
| GET `/rd/work-alert/location-links?id=...` | 取得当前有效的库位关联 | 同时要求原对象和地图权限；无可靠位置返回明确无位置 |
| 服务器内部 JobHandler | 扫描明确启用的租户/规则 | 无公开“扫描任意租户”接口，不接受客户端 tenantId |

初版不新增模型调用接口。解释由规则事实及经过审阅的本地文案构成；若引导进入原包码问答，仍由用户在原入口明确发起、沿用原预算/白名单。

链接返回受控 `sourceType/sourceId/actionCode`；前端从现有路由注册表映射，不能渲染任意服务端 URL。导引只打开原页面，业务确认前仍重验原权限、当前版本和实际成员。

## 7. 岗位与权限

新增提醒查看/知悉能力必须使用专用业务权限，并与原数据权限同时满足；有提醒权限不等于得到原订单、包件或全仓数据。不得改用前端角色名称代替后端鉴权。

| 岗位 | 首版可用能力 | 明确禁止 |
| --- | --- | --- |
| 业务演示 admin/有权管理岗位 | 其原业务授权范围内问数、提醒及导引 | 因新菜单获得系统维护/密钥权限 |
| 生产 | 已授权生产及待检、待入库关联事实和负责事项 | 自动生成质检结论、替仓管确认 |
| 质检 | 已授权质检待复核、实际覆盖成员、原复核入口 | 从同炉/同源未覆盖包推断放行 |
| 仓管 | 已授权上架、库存占用、装车及库位联动 | 点击知悉直接解除锁定或出入库 |
| 叉车司机 | 仅本人实际任务的待办、任务异常和原 PDA 导引 | 全仓问数/地图、其他司机任务、扫码确认、库位更新 |
| 商务 | 其原订单/提货权限范围内的进展与可见限制 | 借提醒入口读取原本无权查看的包件和全仓锁货清单 |
| 只读/领导查看 | 已授权摘要、证据和趋势说明 | 知悉写入、业务处理或默认拥有所有部门数据 |

角色与权限组合变化后重新计算；司机限制不能被通配权限、旧缓存或迟到响应绕过。客户/仓库/部门细粒度范围未落地前，不在页面承诺相应隔离。综合项目部等未建专用账号的岗位先使用核定的查看权限，不临时给管理员角色。

## 8. 页面与交互

### 8.1 小垛

保留左下角入口、现有会话生命周期、键盘、清空和取消。新增受控问题快捷入口、明确的仓库/对象选择，以及“事实、范围、证据、下一岗位、原页面入口”回答结构。原导航和知识回答仍可用。

空结果、无权、来源待核、部分结果、扫描延迟、网络错误分别呈现。未查询不显示为 0；后台处理未结束不显示“已解决”。不记录聊天原文到日志，不在本机持久化新增业务明细。

### 8.2 异常中心

新增计划路由 `/work-alerts`。桌面为可扫描的列表和详情抽屉，按类型、状态、等级及已授权业务范围筛选；手机为稳定尺寸的紧凑列表和全屏详情。具备分页、刷新、来源时间、知悉和进入原业务操作。

## 10. 真实验收场景

| 场景 | 必须观察到的结果 |
| --- | --- |
| A1 合格未入库 | 包件与实际任务分别统计，不把入库派单当入库完成 |
| A2 质检提交超过阈值 | 自动出现一次提醒，实际覆盖成员、submitTime、规则阈值正确 |
| A3 质检通过/不通过复核 | 原岗位办理后提醒重核消除，未覆盖成员不继承结论 |
| A4 正常装车锁定 | 查询能看到占用，但未超过阈值不报异常 |
| A5 超时或终态残留占用 | 展示不同原因和原任务，不自动释放占用或出库 |
| A6 任务未接办/待最终确认 | 各自使用 assignedTime/scanCompleteTime，未填时间待核 |
| A7 点已知悉 | 提醒产生一条有效事件，原库存、质检、任务状态完全不变 |
| A8 原页面处理 | 有权人员在原页面完成允许操作，随后重核更新提醒，流水可追查 |
| A9 点击定位 | 正确仓库、精确 locationId 与层级；无位置明确展示，不能任意放到空库位 |
| A10 司机与商务越权 | 无权问题不泄露总数/包码/库位，深链服务端也拒绝 |
| A11 源服务/扫描中断 | 原提醒保留并标明待核/过期，不突然显示“0异常/全部完成” |
| A12 多端与任务改派 | 重复知悉不多记，过期源版本不覆盖新任务，旧身份不显示新结果 |
| A13 规则阈值变化 | 记录规则版本/原因；规则停用不冒称业务已解决 |
| A14 重启与并发扫描 | 投影/审计不丢，重扫不重复，旧执行器不能回写 |
| A15 原功能回归 | 一包一码、代表扫码、整车任务、配吨/OCR/追溯、二维/双层图、登录和 PDA 返回仍正常 |
